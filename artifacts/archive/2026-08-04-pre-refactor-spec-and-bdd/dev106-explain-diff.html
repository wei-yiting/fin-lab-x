背景

深背景:LLM 的「思考」怎麼流到瀏覽器

若你已熟悉 SSE streaming 與 AI SDK 的 UIMessage Stream Protocol,可直接跳到近背景。

現代的 reasoning model 在回答之前會先「想」。這些 thinking tokens 跟最終答案是兩種不同的輸出:provider 的 API 會分開標記它們,前者告訴你模型正在盤算什麼,後者才是要給使用者看的答案。一次典型的 agent turn 長這樣:

reasoning「先找出 10-K 的章節清單」
→
tool calllist_sec_sections
→
reasoning「Item 1A 在第三節」
→
tool callget_section
→
answer「2024 年新增了…」

這串東西要從後端流到瀏覽器,走的是 SSE(Server-Sent Events)——一條開著不關的 HTTP 連線,伺服器一行一行往下推 data: {...}。相較於 WebSocket,SSE 是單向的、跑在普通 HTTP 上,對「伺服器持續吐東西給前端」這個場景剛好夠用。

前端這邊,FinLab-X 用的是 Vercel 的 AI SDK v6。它的 useChat hook 幫你管理整段對話:你拿到一個 messages 陣列和一個 status。關鍵在於 messages 裡每則訊息不是一坨字串,而是一個 parts 陣列——文字是一個 part、每次 tool call 是一個 part、每段 reasoning 也可以是一個 part。SDK 負責把 wire 上的 frames 組裝進這個陣列。

關鍵概念:UIMessage Stream Protocol

AI SDK 定義了一套 wire format,每個 frame 是一個帶 type 的 JSON。文字走 text-start / text-delta / text-end 三段式;reasoning 也有對應的 reasoning-start / reasoning-delta / reasoning-end。SDK 收到這三種 frame 時,會自動在 message.parts 裡建立、累積、封閉一個 { type: 'reasoning', text, state } 的 part。

另外有一條旁路:任何 data-* 型別的 frame,如果帶了 transient: true,SDK 就不會把它放進 parts,而是丟給你註冊的 onData callback。這是設計給「短暫的、不屬於對話歷史的」訊息用的——例如「正在下載第 3 頁…」這種進度回報。

還有一個之後會咬人的細節:useChat 的 status 只有四個值。

status意思
submitted訊息已送出,還沒收到任何回應
streaming回應正在抵達
ready整段回應收完
error失敗

近背景:改動前 FinLab-X 長什麼樣

這個 repo 原本沒有用 native reasoning parts。它自己蓋了一整套平行的機制,理由是當時的產品裁決:「reasoning 全程不進 transcript」——思考過程只在回答出現前短暫閃現,答案一開始就消失。

為了做到這件事,後端把 reasoning 文字餵進一個 ReasoningSegmenter:

# backend/agent_engine/streaming/reasoning_segmenter.py(已刪除)
_HALF_WIDTH_BOUNDARY = re.compile(r"(?<!\d)[.!?](\s)")
_IMMEDIATE_BOUNDARY  = re.compile(r"[。！？\n]")

class ReasoningSegmenter:
    SOFT_EMIT_CHAR_THRESHOLD = 80  # D26 — 防止 CJK 文字無限緩衝

它在 streaming 的 delta 流上找句子邊界,湊滿一句才吐出來——因為前端那個單行指示器一次只能顯示一句話,半截的句子會看起來很怪。半形標點要求後面跟空白(避免把 3.14 切開),全形標點和換行則立即斷句,再加一個 80 字的軟上限,因為中文常常一長串沒有標點。

切好的句子包成自訂的 ReasoningStatus domain event,序列化成這樣送上 wire:

data-reasoning-status{"id":"reasoning-0","data":{"text":"先找出 10-K 的章節清單。"},"transient":true}
data-reasoning-status{"id":"reasoning-0","data":{"text":"Item 1A 在第三節。"},"transient":true}

注意 transient: true——這正是「不進 transcript」的實作方式:SDK 不會把它放進 parts,所以歷史紀錄裡永遠沒有 reasoning。前端用一個 useReasoningStatus hook 接住 onData,把最新那句話存進一個 useState,舊的直接被蓋掉。

然後問題開始滾雪球。既然這個指示器不是從資料推導出來的、而是一個獨立的狀態變數,就得手動決定它什麼時候該消失。於是有了:

  • 兩個 guard ref(clearedRef / finishedRef),防止 finish 之後還有殘留的 SSE event 把文字塞回來
  • 兩個語意不同的清除動詞:hideReasoningStatus()(輪次中途清,下一輪的 reasoning 還能進來)vs clearReasoningStatus()(整段清掉並上鎖)
  • 一個每秒跑一次的 setInterval,用來偵測「超過 10 秒沒動靜」
  • ChatPanel 裡一個 useLayoutEffect,在 text/tool part 出現時呼叫 hideReasoningStatus()
  • 一個叫 shouldShowReasoningIndicator() 的純函式,裡面是一張條件表,窮舉「last part 是 text/執行中的 tool/完成的 tool/空陣列…」各自該不該顯示

再加上 abort 的處理(凍結成 STOPPED 標籤)、5 個只在測試用但住在 production code path 的 env flag(EMIT_DELAYED_REASONING、STUB_REASONING_ONLY、FORCE_REASONING_NON_TRANSIENT…),還有一層「萬一後端的 transient 壞掉,前端也要濾掉 data-reasoning-*」的防禦。一次 over-engineering 稽核數出19 個 UX state、約 2,000 行程式碼。

為什麼要推翻原本的設計

真正的致命傷不是行數,是產品方向。FinLab-X 的 roadmap 是多輪 tool loop(reason → tool → reason → tool → answer)。ephemeral 指示器下,第 2 輪之後的思考全部看不見、事後也無從查證。

2026-07-24 的一次 UX 調查發現:ephemeral-only 是單答型 chat 的慣例(ChatGPT、Gemini、Perplexity——答案開始後 thinking 不再出現);而所有把 multi-step agent 攤開給使用者看的產品(Claude.ai、Cursor、Claude Code、Copilot agent mode)都保留一個會反覆出現的持久 thinking 面。原本快要出貨的組合——「會重新跳出來的 ephemeral 指示器」——是沒有任何產品採用的第三種。這個發現變成 ADR-0006。

核心直覺

把狀態機換成推導

整個改動可以濃縮成一句話:協定裡已經有這條頻道了,不要自己再發明一條。

後端不再切句子、不再包 data-*,直接把 provider 的 delta 原樣轉成 native frames:

reasoning-start{"id":"reasoning-0"}
reasoning-delta{"id":"reasoning-0","delta":"先找出 10-K"}
reasoning-delta{"id":"reasoning-0","delta":" 的章節清單"}
reasoning-end{"id":"reasoning-0"}
tool-input-available{"toolCallId":"tc-1","toolName":"list_sec_sections"}
reasoning-start{"id":"reasoning-1"}

沒有句子邊界的概念了——delta 進來多少就送多少,前端用 white-space: pre-wrap 原樣渲染。segmenter 的 80 行 regex 直接刪掉。

而 SDK 收到這些 frame 後,會把 reasoning 組裝進 message.parts。這一步是所有後續簡化的槓桿點:reasoning 一旦變成資料,UI 就全部可以用推導的。

看一個具體例子。假設此刻 status === 'streaming',而最後一則 assistant 訊息的 parts 是:

[
  { type: 'reasoning', text: '先找出 10-K 的章節清單',  state: 'done' },
  { type: 'tool-list_sec_sections', state: 'output-available' },
  { type: 'reasoning', text: 'Item 1A 在第三…',        state: 'streaming' },
]

從這個陣列 + status,不需要任何額外記錄,就能算出整個畫面:

從上面那個 parts 陣列推導出來的畫面
比較 Apple 2024 vs 2023 的 Item 1A
▶ Thought for 3s
✓ list_sec_sections
▼ Thinking…
先確認章節編號對應 Item 1A 在第三…

推導規則很短:state === 'done' → 收合成 Thought for Xs;state === 'streaming' → 展開、釘底、標 Thinking…。tool part 照 parts 的順序夾在中間。「只有當前輪展開」不需要任何額外邏輯——前一顆 chip 之所以收合,只是因為它的 state 已經變成 done 了。

關鍵概念:非 derived state 預算

純推導的架構要有紀律才守得住,所以這個 slice 明訂了一份「允許存在的非推導狀態」清單,任何新增都要過裁決:

  1. chip 計時 map —— parts 上沒有 timestamp,「想了幾秒」只能 client 自己量
  2. 全域 stall 碼表 —— 「10 秒沒動靜」是時間的函數,不是資料的函數
  3. 展開/收合 override map —— 使用者手動點開的意圖必須蓋過推導
  4. placeholder grace timer —— 後來才加的第 4 個(下面會解釋為什麼跑不掉)

共通點:這四個存的都是協定沒有攜帶的資訊(時間、使用者意圖)。凡是 wire 上已經有的,一律不准另存一份。

abort 偵測不需要任何狀態

使用者按下 Stop 的時候,畫面該怎麼呈現那顆「想到一半」的 chip?

直覺會想:記一個 abortedMessages set,把被中斷的 message id 記進去。舊版就是這麼做的。但在 native parts 底下,有個更漂亮的答案——中斷這件事已經寫在資料的形狀裡了。

理由是:abort 會直接把 wire 關掉,所以 reasoning-end 永遠不會抵達。SDK 因此把那個 part 的 state 留在 'streaming'。與此同時,useChat.status 已經離開了 streaming/submitted 這對活躍狀態。這個組合在正常情況下不可能出現:

part.statechat 活躍中?推導結果
'streaming'是正在思考 → Thinking…
'streaming'否被中斷 → Stopped — thought for 23s
'done'任意正常完成 → Thought for 12s
// frontend/src/lib/reasoning-chips.ts
export function chipStateOf(part: ReasoningPartLike, chatActive: boolean): ChipState {
  if (part.state === "streaming") {
    return chatActive ? "streaming" : "aborted";
  }
  return "done";
}

五行,取代了整組 abortedMessages 追蹤。順帶一提,這也自動處理了一個容易漏掉的邊界:如果是錯誤而不是中斷,而且 reasoning-end 已經送達了,那 state 就是 'done'——chip 會維持乾淨的 Thought for Xs,錯誤訊息另外用 error 面呈現,不會誤標成「被中斷」。

placeholder:兩個空窗

舊的 ActivityIndicator 縮編成一個純粹的補洞元件。它的職責只剩一句話:當畫面上沒有任何「活的」元素時,給使用者一個「還在跑」的訊號。

一輪對話裡有兩段這樣的空窗:

wire (等待) reasoning ① tool answer
placeholder 空窗 (a) (b)

空窗 (a) 是送出之後、第一個看得見的東西出現之前。空窗 (b) 是某顆 chip 收合了、但下一個東西還沒來。其他時候一律隱藏——chip 正在串流時它自己就是活元素,tool card 執行中也是(tool card 有自己的進度顯示,decision 5 明訂那個微小的空檔不出 placeholder)。

空窗 (b) 有個討厭的地方:chip 收合的那一刻,前端無從得知下一個 part 會是 tool card(不該出 placeholder)還是 answer text(該出)。wire 上沒有 lookahead。這就是第 4 個非推導狀態 PLACEHOLDER_GRACE_MS = 300 的由來——用經驗解決:tool part 通常在收合後幾毫秒內就到,只有真正的空窗撐得過 300ms。

誠實記錄:這是一個未經裁決的機制

300ms grace delay 從來沒有進過正式的設計裁決,是實作時發現「wire 無法區分兩種情況」後不得不加的。code review 兩軸都各自標記了它——不是要求移除(reviewer 同意這是唯一可行解),而是要求文件不能繼續宣稱「恰好三個非推導狀態」。這類「實作被迫偏離規格」的項目,重點不在對錯,而在不能讓它悄悄消失在 code 裡。

三個 bug,以及它們為什麼難抓

實作完成、測試全綠、two-axis review 過關之後,人工實測跟後續三輪 code review 又抓出三個 bug。這三個特別值得看,因為每一個都是「推導模型」的微妙後果——不是打錯字,是模型本身的邊界沒想清楚。

Bug 1:空窗 (a) 提早結束

規格白紙黑字寫著:空窗 (a) 綁在 status === 'submitted',而且明確排除「streaming 且 parts 為空」的寫法。實作照做了。人工測試時卻看到:placeholder 消失後、第一顆 chip 出現前,有一段肉眼可見的空白,看起來像壞掉。

root cause 在 status 的語意:它在 wire 的第一個 frame(start)就從 submitted 翻成 streaming。但那個 frame 不帶任何看得見的內容。實測第一個 reasoning-delta 可以晚上將近 8 秒才到。

wire frames 連線中 start (沒東西) reasoning-delta…
status submitted streaming
修正前 placeholder 一片空白 😞 chip
修正後 placeholder chip

修法是把空窗 (a) 的判斷從「status 是什麼」改成「畫面上有沒有東西」:

const windowA =
  status === "submitted" ||
  (status === "streaming" &&
    (!last || last.role !== "assistant" || !turnHasRenderableContent(last)));

turnHasRenderableContent() 只認三種東西:非抑制的 reasoning chip、tool card、非空的 text。reasoning-start 建立了 part 但還沒有 delta?不算。這個判斷是單調的——part 一旦畫出來就不會消失——所以不需要 grace delay,不會中途閃回。

流程問題,不只是技術問題

這個修正在工程上是對的(兩輪獨立的 spec review 各自確認過方向正確)。但它是先斬後奏:規格是三天前經過正式 Three Amigos 討論裁決的,而修正直接改 code、事後才在 Linear 留言說「我改了,順帶這牴觸了先前的裁決」。結果是 bdd-scenarios.md 跟 code 有一段時間各說各話。

review loop 把這件事標成 Major 並不是要求回退,而是要求權威文件必須追上現況——最後在 bdd-scenarios.md 補了 superseded 標記,完整的裁決紀錄收斂則明確掛給 DEV-108。

Bug 2:計時 map 被整批清空

「想了幾秒」是 client 量的,存在一個 Map 裡,key 是 messageId:partIndex。ChatPanel 有個 resetForNewTurn(),在每次送出 / regenerate / retry 時被呼叫,裡面做兩件事:清空展開 override map(對的,規格要求每輪重置),以及清空整個計時 map(錯的)。

為什麼錯?因為計時 map 的 key 已經用 message id 隔離了,而每次 render 時 observe() 會掃過全部訊息重新推導計時——包括畫面上還在的舊訊息。

送出第二個問題的瞬間
比較 Apple 2024 vs 2023
▶ Thought for 0s  ← 剛才明明是 3s
✓ list_sec_sections
2024 年新增了三項風險因子…
那 Microsoft 呢?
Thinking

連鎖反應是:map 清空 → 舊 chip 找不到自己的計時 → observe() 用當下的 wall clock 幫它重建一筆 → 但舊訊息的那個 reasoning part 後面早就有其他 part 了,所以「凍結條件」立刻成立 → 凍結在 now - now = 0。歷史紀錄上的 Thought for 3s 就這樣變成 Thought for 0s。

修法:resetForNewTurn() 不再碰計時 map;只有 handleClearSession()(整段對話重置,畫面全空)保留全清。另外查證了 AI SDK 原始碼確認 regenerate() 不會重用舊的 assistant message id,所以不需要額外的 per-message 清理。

為什麼測試沒抓到

當時的 integration test 斷言是 /\d+s/——一個寬鬆的 regex,而 "Thought for 0s" 完全符合。修正時把它改成:送出第二個問題之前先抓下那串文字,之後斷言它逐字不變。這個新斷言用 git stash 回退到修正前的 code 驗證過,確認真的會 fail——不然「加了測試」只是自我安慰。

Bug 3:tool 參數提前關閉 reasoning

這個是 code review 抓到的,而且是三次 review pass 裡只有一個模型看見的那種。

裁決 S-chip-06 說:當 provider(Gemini 尤其常見)在 reasoning-end 之前 就開始送 tool 參數時,tool card 應該渲染在還開著的 chip 下方,維持 part 抵達順序,不強制立即收合。

但後端的 mapper 第一行就把 reasoning 關掉了:

def _handle_tool_call_chunk_block(self, block, events):
    self._close_reasoning_part(events)   # ← 無條件關閉
    ...

結果 wire 上永遠不可能出現「chip 還開著、tool 已經來了」的狀態:

reasoning-delta{"id":"reasoning-0","delta":"我需要查一下章節"}
reasoning-end{"id":"reasoning-0"} ← 提前送出,chip 立刻收合
tool-input-available{"toolCallId":"tc-1",...}

更糟的是,單元測試把錯誤行為當成正確答案鎖住了:

def test_tool_call_chunk_closes_open_reasoning_part(self):
    ...
    assert events == [ReasoningEnd(reasoning_id="reasoning-0")]

所以「測試全綠」在這裡完全沒有保護力——測試忠實地驗證了一個違反裁決的行為。

修法是刪掉那一行。之所以安全,是因為 reasoning part 早就有四個正確的關閉邊界:

關閉時機負責的程式碼
text block 抵達(模型開始寫答案)_handle_text_block()
下一輪 LLM call(chunk.id 轉換)_handle_messages() 的 id-transition guard
同一 chunk 內第二個 reasoning block(OpenAI multi-summary)force_new_part 參數
整輪結束finalize()

測試同步改寫成 test_tool_call_chunk_does_not_close_open_reasoning_part,並新增一個 test_tool_call_chunk_then_new_llm_call_closes_part_exactly_once 驗證 part 最後仍然恰好關閉一次——不是不關,是在對的地方關。

為什麼這個 bug 難抓

它跨了兩層。「tool card 排在 chip 下方」聽起來是前端排版問題,所以前面幾輪 review 都在看 AssistantMessage.tsx 的渲染邏輯——而那邊確實是對的(它忠實按 parts 順序畫)。問題在後端根本沒讓那個狀態發生。要抓到它,得同時握著「裁決說什麼」和「wire 上實際會出現什麼序列」兩件事。

def _handle_reasoning_block(self, block, events, force_new_part=False):
    if force_new_part:
        self._close_reasoning_part(events)
    if self._open_reasoning_id is None:
        self._open_reasoning_id = f"reasoning-{self._reasoning_id_counter}"
        self._reasoning_id_counter += 1
        events.append(ReasoningStart(reasoning_id=self._open_reasoning_id))
    delta = block.get("reasoning", "")
    if delta:
        events.append(ReasoningDelta(reasoning_id=self._open_reasoning_id, delta=delta))
邊界情況:part id 必須 turn-unique

AI SDK 在 finish-step 時會重置它內部的 active-part map,允許 id 跨 step 重用。如果後端依賴 SDK 層級的唯一性,多輪 tool loop 會撞 React key 和計時 ref。所以這裡用一個 per-request 的 counter(reasoning-0、reasoning-1…),整輪不重置。這條是實作前查 Context7 文件才發現的,不是憑記憶。

這個設計後來咬了 E2E 一口

因為點點是 CSS 生成內容,DOM 的 textContent 只有 "Thinking"——沒有省略號。而 E2E 還在斷言 toHaveText("Thinking…")。Playwright 的 toHaveText 預設比對 textContent,不含 ::after,所以那個測試必定失敗。它躲過了整個 CI 前的驗證,因為當時只跑了 vitest + tsc + eslint——沒人跑 Playwright。抓到之後是實際裝了瀏覽器跑一次確認,不是憑推論。
